# 决策压力测试

用户要求的思考顺序：先禁止支持、全力反驳；再切换支持；最后中立对照证据，明确优势与反转条件。把“全力反驳”理解为寻找最强、可信的反对论证，不能理解为结论必须反对。

## 适用范围与时机

在访谈充分理解真实目标后、定稿方案之前使用。重大范围变更、采购/持续成本、数据库与部署、登录权限、支付、多租户和生产发布也适用。用户只要求简单改字、对齐图标时直接完成，不添加整套决策仪式。

访谈中可以用一句解释引出下一问，但每次只问一个问题；关键答案未齐时不假装已经完成裁决。

## 1. 反方：暂缓认同，找出决定最可能失效的位置

按实际相关性检查，不机械凑满每项：
- **缺失事实**：谁付钱、谁使用、哪个环节节约时间、有无真实样本、现有系统能否覆盖。
- **乐观假设**：把测试人数当真实并发、把优惠首年价当长期年费、把“上线”当所有功能已经充分验收。
- **不可逆成本**：数据格式/账号绑定迁移、公开承诺、付费长期资源、真实业务修改；可回滚的页面原型不要夸大成不可逆。
- **机会成本**：是否值得先做自动支付、复杂 AI、多租户，而不先验证预约和运营闭环；包括时间、预算、维护负担与推迟上市。
- **最坏可信风险**：数据串户、重复扣费/入账、备份无法恢复、模型费用失控。说明触发条件、影响和证据，不把所有想象都当作现实概率。
- **认知偏差可能性**：只有用户表述提供依据时，指出可能的沉没成本、确认偏差、因熟悉而低估迁移难度；措辞保留不确定性，不做心理诊断。

对每个主要反对点写明：证据或假设 → 影响 → 可采取的方向。例如：“只看到单实例快照恢复，尚无多实例一致性依据；若需多副本，应考虑托管数据库，或明确限制单实例并验证可接受的恢复窗口。”

## 2. 支持方：给出最强成立理由

结合实际目标和约束，解释为什么这个方案可能值得做。包括已经验证的需求、现有资源、低迁移成本、短期预算、可控规模、可逆试点和明确差异化。不能只复述“便宜、好看、用户喜欢”。说明支持理由依赖的前提。

## 3. 证据裁决

把事实、用户判断、待验证假设分开。分别说明证据来源、时间、适用环境和限制；部署截图与客户完整闭环的证明力不同。

明确输出：
- 目前支持/反对/暂缓哪一项，占优势的关键证据是什么。
- 最大未知风险是什么、影响哪条结论、如何验证。
- 出现什么**可观察条件**结论会反转；避免虚构精确并发阈值或价格。
- 不强行五五开。事实明显支持某方就直说；信息不足就说明尚不能裁决。

## 4. 推荐与行动

首选给一个方向，必要时一个备选，并解释何时切换。最小验证可为用户访谈、样本迁移、隔离负载测试、恢复演练、预算测算。若某项是强制平台条件或安全不变量，明确不能用较低成本交换掉它。

不擅自执行采购、公开发布、删除或真实业务迁移。当前任务已授权的本地实现与验证可继续。

## 两个例子（不是新项目的预设结论）

**“用存储桶省掉数据库”**
反方：对象存储不提供应用所需的数据库事务，单实例 SQLite 快照不能共享多实例实时写入。
支持：在低写入量、单实例且允许按最近快照恢复的明确条件下，快照备份可降低基础费用。
裁决：根据写入并发、可容忍损失和恢复时间选型；先测恢复，再决定。需要多个写实例或更严格一致性时转向托管数据库。

**“先做一个所有行业都能卖的系统”**
反方：行业角色、履约和监管不能靠改名字统一，早做万能功能会增加维护与验证成本。
支持：三端边界、权限基础、附件、错误处理和发布工具确实能共用。
裁决：先提炼通用工作流与可选模块，用两个不同领域的新项目检验适配；租户需求明确后再设计共享 SaaS。
